# GRACE-ARP-INSTRUCTIONS.md

## Для чего нужен этот файл

Положи этот файл в корень проекта, в котором создаются или изменяются GRACE-артефакты. Он кратко объясняет исполнителю — человеку или ИИ — как готовить артефакты, чтобы GRACE-ARP мог проверить их и построить C1–C3.

- `docs/` — базовая методология GRACE и источник смысла требований.
- `docs/profiles/arp/GRACE-ARP.md` — обязательный профиль автоматической проверки и построения C1–C3.
- Этот файл — краткая рабочая инструкция. Он не заменяет исходные требования и не разрешает придумывать отсутствующие решения.

## Источники для C1–C3

- **C1 — System Context:** `RequirementsAnalysis.xml`.
- **C2 — Container:** `Technology.xml` вместе с `DevelopmentPlan.xml`.
- **C3 — Component:** Module Contracts с архитектурным контекстом и размещениями из `DevelopmentPlan.xml`.
- Предварительные исследования и открытые вопросы могут храниться как вспомогательные материалы проекта, но `TechnologyAnalysis.xml` не является обязательным артефактом базовой методологии GRACE. Утверждённые технологические решения фиксируются в `Technology.xml`.

Не используй артефакт следующего этапа, чтобы молча заполнять пробелы предыдущего. Сохраняй утверждённый смысл и стабильные уникальные `id`; все обязательные ссылки должны разрешаться однозначно.

## Обязательные соглашения GRACE-ARP

Эти требования относятся к профилю GRACE-ARP. Не представляй их как XML-конструкции, которые обязательно определены самой базовой методологией GRACE.

### C1 — `RequirementsAnalysis.xml`

- Используй `PROJECT_GOAL` для цели системы.
- Связывай актор со сценарием вложенным элементом `ACTOR ref="ACTOR-ID"` внутри `USE_CASE`. Не заменяй его на `ACTOR_REF` или `SUPPORTING_ACTOR_REF`, если отдельная утверждённая поддержка этих элементов не реализована.
- Если актор участвует в сценарии согласно требованиям, связь должна быть явной. Объявленный, но не связанный с `USE_CASE/ACTOR` актор вызывает предупреждение и не создаёт связь с системой.
- Каждую внешнюю программную систему объявляй отдельным верхнеуровневым `EXTERNAL_SYSTEM` с уникальным `id` и непустым названием. Одного `ACTOR kind="external-system"` недостаточно.
- Каждое утверждённое взаимодействие с ней задавай отдельным верхнеуровневым `SYSTEM_INTERACTION` с уникальным `id`, `external_system_ref`, `direction` и непустым `PURPOSE`.
- `external_system_ref` должен ссылаться на объявленный `EXTERNAL_SYSTEM`. Допустимые направления: `SYSTEM_TO_EXTERNAL` и `EXTERNAL_TO_SYSTEM`; выбирай только подтверждённое требованиями направление.
- При известном названии укажи `system_name` у корневого `REQUIREMENTS_ANALYSIS`. Не считай имя репозитория доказательством семантического названия системы.

### C2 — `Technology.xml` и `DevelopmentPlan.xml`

- Отображай C2-элемент только если утверждённые артефакты однозначно определяют его как самостоятельное приложение/исполняемую единицу или хранилище данных. GRACE-модуль автоматически не является C2-элементом.
- Для каждой связи явно задай идентификаторы концов, смысл и направление. Для внутренних связей используй соответствующее направление:
  - приложение → приложение: `APP_TO_APP`;
  - приложение → хранилище: `APP_TO_DATA_STORE`;
  - хранилище → приложение: `DATA_STORE_TO_APP`;
  - хранилище → хранилище: `DATA_STORE_TO_DATA_STORE`.
- Для поддерживаемых интеграций используй `APP_TO_EXTERNAL` или `EXTERNAL_TO_APP` с правильной ориентацией концов. Не придумывай связь или направление по названиям, технологии, коду или близости XML-элементов.
- Размещение GRACE-модуля в C2 задавай явно через `PLACEMENT c2_ref="C2-ID"` внутри соответствующего `MODULE` в `DevelopmentPlan.xml`. Не выводи размещение из использования хранилища или зависимостей.
- Не создавай архитектурные элементы только потому, что технология или поставщик упомянуты в требованиях.

### Семантическая целостность DevelopmentPlan.xml

- Объявляй каждый MODULE один раз внутри единственного MODULES; ID модулей должны быть уникальными.
- В MODULE_DEPENDENCIES указывай source_ref и target_ref только на объявленные MODULE. Самозависимости и циклы запрещены. Несколько отдельных зависимостей между одной парой модулей допустимы, если у каждой собственные ID и PURPOSE.
- В DATA_FLOWS задавай не менее двух STEP с уникальным непрерывным order от 1 до N. Каждый module_ref должен ссылаться на MODULE. Повторное участие одного модуля допустимо и не удаляется. Указывай PURPOSE, SUCCESS_RESULT и FAILURE_RESULT.
- В STATE_MODEL объявляй локальные STATE непосредственно внутри STATE_MACHINE либо используй USES_STATE для ссылки на STATE из RequirementsAnalysis.xml/STATES. Каждый TRANSITION должен ссылаться на состояния той же машины через from и to. Не заявляй достижимость или детерминизм переходов: текущая XML-модель не задаёт начальное состояние и машинно-читаемые события/условия.
- В IMPLEMENTATION_SEQUENCE нумеруй PHASE непрерывно от 1. Указывай ровно по одному GOAL, DELIVERABLES и CHECKS. Явные предпосылки задавай через DEPENDS_ON ref="PHASE-ID"; каждая предпосылка должна ссылаться на более раннюю фазу. APPROVAL_GATE, если присутствует, использует SATISFIED, PENDING или BLOCKED.
- В RISKS указывай severity из BLOCKING, HIGH, MEDIUM, LOW; status из OPEN, MITIGATED, ACCEPTED, RESOLVED. Если status отсутствует, он трактуется как OPEN. Каждый риск должен иметь описание и один непустой MITIGATION.
- Не выводи смысл из названий или свободного текста. Валидатор проверяет точные XML-элементы, атрибуты, ID-ссылки и целочисленный порядок. Любое нарушение этих правил блокирует validate и generate для C2/C3.

### C3 — Module Contracts

- Каждый `MODULE_CONTRACT` должен содержать ровно один `GRACE_MODULE ref="MOD-ID"` внутри `LINKS`; ссылка должна разрешаться ровно в один `MODULE/@id` из `DevelopmentPlan.xml`.
- `USES ref="MOD-ID"` может задавать связь C3 только при однозначной ссылке на GRACE-модуль и соответствии правилам профиля.
- Ссылки трассировки на требования, процессы, инварианты и Function Contracts сами по себе не являются архитектурными стрелками.

## Порядок проектирования и создания XML-артефактов

Эти правила обязательны **до начала написания XML** и при каждом последующем изменении. Валидатор — заключительная проверка готовой модели, а не средство подбора структуры методом проб и ошибок.

### 1. Сначала определи допустимую структуру

До создания или изменения артефакта:

1. Определи его назначение, границы и содержание по GRACE.
2. Проверь обязательные соглашения GRACE-ARP и утверждённые решения проекта.
3. Установи, какие XML-элементы и атрибуты разрешены для этого артефакта, где они могут находиться, что означают и какие связи выражают.
4. Различай базовые правила GRACE, обязательные расширения GRACE-ARP и локальные решения проекта. Не переноси конструкцию из примера или другого артефакта, если её применимость здесь прямо не установлена.

Используй только структуру, определённую GRACE, GRACE-ARP или отдельно утверждённой спецификацией данного артефакта. Если нужное содержание невозможно выразить предусмотренными конструкциями, **не изобретай XML-тег, атрибут или способ связи**. До редактирования сформулируй недостающее структурное решение и запроси его утверждение.

### 2. Составь реестр сущностей до написания XML

До генерации XML перечисли логические сущности, которые должны присутствовать в артефакте. Для каждой определи:

- тип и смысл сущности;
- артефакт и единственное место её канонического объявления;
- XML-элемент, которым это объявление разрешено выражать;
- стабильный ID;
- предусмотренные атрибуты состояния и содержания;
- допустимые ссылки на неё и из неё.

Отдельно классифицируй каждый элемент модели: это самостоятельная сущность, связь между сущностями, свойство существующей сущности или только её отображение в списке/сводке. Разные имена XML-тегов сами по себе не означают, что за ними стоят разные сущности.

Реестр может быть рабочей таблицей автора и не обязан становиться частью XML. Он нужен, чтобы до записи документа обнаружить повторные объявления и не предусмотренные моделью связи.

### 3. Объявляй каждую логическую сущность один раз

1. У каждой логической сущности должно быть одно каноническое объявление в установленном для неё месте.
2. В пределах одного XML-артефакта каждое значение атрибута ID должно встречаться ровно один раз — независимо от имени элемента, вложенности и раздела.
3. Повторное включение сущности в перечень, индекс, сводку, дорожную карту или другой раздел не создаёт новую сущность и не даёт права повторно объявить её с тем же ID или назначить ей новый ID.
4. Состояние, статус или краткое представление уже объявленной сущности должны относиться к её каноническому объявлению, если утверждённая модель не определяет их как самостоятельные сущности.
5. Если документу необходимо повторно упомянуть сущность, используй только явно предусмотренный для этой пары типов механизм ссылки. Если такого механизма нет, не создавай второе объявление: измени проектируемую структуру так, чтобы сохранить одно объявление, либо запроси утверждение необходимого расширения.

### 4. Назначай ID и создавай ссылки по модели

- Назначай ID при создании новой логической сущности. ID должен быть уникальным в установленной области идентичности и сохраняться при изменении описания, статуса, порядка или места отображения сущности.
- Не назначай новый ID существующей сущности только потому, что её нужно показать в другом разделе или представить другим XML-тегом.
- Создавай ссылку только через атрибут или XML-элемент, нормативно предусмотренный для конкретных типов источника и цели.
- До записи ссылки проверь, что известны её область разрешения, допустимый тип цели и правило разрешения. Цель должна быть объявлена один раз и однозначно идентифицироваться предусмотренным ID.
- Не используй имена, заголовки, пути к файлам или произвольные строки вместо ID, если соответствующее правило явно не устанавливает такой формат.

### 5. Изменяй существующие артефакты без размножения сущностей

Перед изменением прочитай артефакт целиком и найди все связанные с изменяемой сущностью объявления и ссылки. Изменяй её каноническое объявление на месте. Не добавляй параллельное объявление ради нового статуса, этапа, представления или группировки. Если изменение действительно вводит новую логическую сущность, назначь ей отдельный ID и установи предусмотренные моделью связи с существующими сущностями.

### 6. Проверь модель до передачи результата

До запуска валидатора проверь весь XML:

1. Каждая логическая сущность имеет одно каноническое объявление.
2. Все значения ID уникальны в пределах артефакта.
3. Каждый тег, атрибут, уровень вложенности и способ связи предусмотрен применимыми правилами.
4. Каждая ссылка использует допустимый механизм, разрешается ровно в одну цель и указывает на цель ожидаемого типа.
5. Сводки, перечни и другие представления не создают повторных объявлений сущностей.

После этой проверки выполни команду `grace-arp validate --project <путь-к-проекту>` и устрани все диагностированные ошибки. Повторяй полную проверку после каждого изменения. Успешная валидация не заменяет предварительное проектирование структуры и проверку смысла модели.

## Правила для исполнителя

1. Прочитай этот файл перед созданием или изменением GRACE-артефактов.
2. Опирайся на утверждённые требования и решения; не вводи новые продуктовые требования.
3. Не выдумывай акторов, внешние системы, взаимодействия, направления, границы, концы связей, владельцев модулей или размещения ради прохождения проверки.
4. Если сведения отсутствуют, противоречивы или допускают несколько трактовок, укажи конкретный пробел и запроси решение ответственного человека.
5. Перед передачей результата выполни `grace-arp validate --project <путь-к-проекту>`, разберись со всеми ошибками и предупреждениями, затем сгенерируй требуемые представления и проверь результат.
6. Успешный разбор XML или генерация DSL сами по себе не доказывают семантическую полноту модели. Не меняй смысл утверждённых требований ради успешной проверки.

**Короткая инструкция для ИИ:** соблюдай GRACE как базовую методологию, GRACE-ARP как обязательный профиль, а этот файл — как практический чек-лист. Применяй правила до написания артефактов. При неоднозначности не угадывай и не исправляй исходный смысл самостоятельно.
