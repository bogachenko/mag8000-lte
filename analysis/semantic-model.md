## 2. Что предписывает GRACE и что уже формализовано

GRACE § 4.1 определяет содержание RequirementsAnalysis:

- цель системы;
- акторы;
- сценарии Actor–Action–Goal;
- бизнес-процессы;
- сущности;
- состояния;
- бизнес-правила;
- ограничения;
- инварианты;
- ошибочные сценарии;
- граничные случаи;
- критерии правильного результата;
- связи между элементами.

В XML-примере GRACE явно показаны конструкции:

- `REQUIREMENTS_ANALYSIS`;
- `PROJECT_GOAL`;
- `ACTOR`;
- `USE_CASE` с вложенными `ACTOR`, `ACTION`, `GOAL` и `STARTS_PROCESS`;
- `BUSINESS_PROCESS` и `STEP`;
- `INVARIANT`.

Пример не является полной XML-схемой. В базовом GRACE не найдена исчерпывающая XML-спецификация объявления и связывания сущностей, состояний, бизнес-правил, ограничений, ошибочных сценариев, граничных случаев и критериев результата.

GRACE-ARP отдельно формализует C1-взаимодействия с внешними программными системами через верхнеуровневые `EXTERNAL_SYSTEM` и `SYSTEM_INTERACTION`, атрибуты `external_system_ref`, `direction` и вложенный `PURPOSE`. Это утверждённое расширение профиля, а не конструкция базового GRACE.

Следствие: семантическую классификацию можно выполнить сейчас, но недостающие XML-конструкции нельзя изобретать. До создания XML для таких категорий требуется отдельное нормативное решение и его утверждение.

### Акторы

В исходнике не найдено однозначного Actor–Action–Goal-сценария, в котором человек непосредственно взаимодействует с MAG8000-LTE как с системой в области рассмотрения.

- Customer в adr-10347 запускает сертификационный процесс через Web APP. Это не доказывает прямое взаимодействие Customer с модулем.
- Customer в adr-10337 выбирает маску тревог, но интерфейс и способ взаимодействия не указаны.
- User в adr-10342 упоминается в инструкции по извлечению SD-карты, но это не задаёт полноценный Actor–Action–Goal-сценарий.

Поэтому новые `ACTOR` и `USE_CASE` пока не создаются. Отсутствие подтверждённого актора не компенсируется его предположительным добавлением.

Этого недостаточно, чтобы без дополнительных решений объявить полноценные автоматы состояний: не все переходы, события, начальные состояния и условия определены.

## 7. Кандидатная структура семантического графа

На основании исходника можно подготовить следующие смысловые кластеры. Это связи для анализа, а не уже утверждённые XML-связи.

1. **Host data acquisition:** MAG8000/host device → Modbus registers → measurement data → CSV/process values.
2. **Analog inputs:** voltage inputs → acquisition control → slope/offset → calculated values → measurement data.
3. **Collection and storage:** DataCollectionInterval → process values → SD/SPI buffering → historical data and overflow handling.
4. **Transmission:** TransmissionInterval / PagingInterval / AutoAdaptiveControl → selected network technology → SMTP/FTP/MQTT data transfer.
5. **Alarm handling:** network signal / faultstatus / module alarms → threshold and mask rules → timestamped alarms → MQTT Broker.
6. **Configuration and device description:** EDD → parameter names and firmware version → configuration through the stated channels.
7. **Clock synchronization:** thingstream server → UNIX-UTC time → module clock.
8. **Leakage detection:** start/period/control parameters + excitation frequency → test scheduling and execution.
9. **Commissioning and hot swap:** first plug-in, power-up indication, FunctionButton, SD-card handling and data-persistence caveat.
10. **Product constraints:** electronics, SIM/eSIM, antenna, enclosure configurations, environmental range and spare parts.

## 8. Что уже можно и чего пока нельзя утверждать

### Можно утверждать по исходнику

- Три C1-взаимодействия, уже внесённые в XML, имеют прямые подтверждения в adr-10353, adr-10341 и adr-10406.
- Источник прямо связывает обозначения host device и TRN в adr-10354; adr-10383 называет регистры MAG8000, а PROJECT_GOAL — MAG8000 Transmitter. Их полное тождество остаётся неподтверждённым.
- В источнике есть явные условные правила, численные границы, форматы данных и сценарии деградированного режима.
- Несколько Feature относятся к комплектации, документации или производству, а не к поведению программного модуля.
- Для двух Feature отсутствует ReqIF.Text; принятое решение baseline запрещает подменять его содержимым ReqIF.ChapterName.

### Нельзя утверждать без дополнительных решений

- Что Customer является Actor именно системы MAG8000-LTE.
- Что cloud based solution или MQTT configuration channel — конкретный внешний программный участник с уже известным именем.
- Что MAG8000 Transmitter, host device и TRN — одна сущность без подтверждения владельца требований.
- Что физический Transmitter можно объявить как `EXTERNAL_SYSTEM`: соглашение GRACE-ARP C1 предназначено для внешних программных систем и не задаёт представление внешнего аппаратного устройства.
- Что упомянутые в source Feature понятия уже имеют однозначные XML-элементы и атрибуты в базовом GRACE.
- Что из описанных параметров автоматически следует полностью определённый конечный автомат.
- Что 26 отношений fulfills можно перенести в семантический граф при отсутствующих целях.
- Что содержимое ChapterName у adr-10361 и adr-10363 является текстом требования: по принятому baseline оба ReqIF.Text остаются пустыми.

## 9. Замечания к текущему RequirementsAnalysis.xml

Текущий XML содержит цель, три подтверждённых внешних взаимодействия и три инварианта, перенесённых из adr-10337, adr-10389 и adr-10397.

Пустой `<ACTORS />` удалён: базовый пример GRACE объявляет `ACTOR` непосредственно внутри `REQUIREMENTS_ANALYSIS`, а подтверждённых человеческих акторов и AAG-сценариев пока нет. Не добавлялись пустые контейнеры, неподтверждённые акторы или сценарии.

В XML использованы только уже показанные базовые конструкции GRACE (`PROJECT_GOAL`, `INVARIANT`) и утверждённые GRACE-ARP конструкции C1 (`EXTERNAL_SYSTEM`, `SYSTEM_INTERACTION`). Схема для сущностей, состояний, бизнес-правил, ошибочных сценариев и граничных случаев не расширялась.

## 10. Следующий шаг

До расширения `RequirementsAnalysis.xml` остаются два решения владельца требований и одно ограничение модели:

1. Подтвердить, относится ли MAG8000 Transmitter из `PROJECT_GOAL` к тому же физическому устройству, что `host device (TRN)` из adr-10354 и MAG8000 Modbus registers из adr-10383; выбрать каноническое имя.
2. Определить, является ли условие «ниже 15 минут» из adr-10358 устаревшим/избыточным относительно условия «ниже 30 минут» из adr-10359 либо относится к отдельному режиму. До решения сохранять оба исходных утверждения; 30-минутное условие логически строже.
3. Если физический Transmitter должен отображаться в C1, отдельно утвердить способ представления внешнего аппаратного устройства: текущая GRACE-ARP конструкция `EXTERNAL_SYSTEM` предназначена для внешних программных систем.

Вопросы, уже закрытые решением `SOURCE_BASELINE_ACCEPTED`, не запрашиваются повторно: `ReqIF.Text` остаётся основным полем, adr-10361 и adr-10363 остаются с пустым текстом, а отсутствующие внешние документы не используются для дополнения baseline. Все 70 Feature остаются в объёме анализа.

После этих решений продолжить формализацию бизнес-правил, сущностей, состояний, ошибочных сценариев и критериев результата. Если для категории нет утверждённой XML-конструкции в GRACE или GRACE-ARP, до записи XML потребуется отдельное структурное решение.

Ни одно исходное Feature не исключается из области анализа из-за отсутствия решения по его семантике.
