# 7. AI-контракт, DbC и docstring

Классический Design by Contract в основном описывает:

```text
предусловие → команда → постусловие
```

AI-контракт шире. Его задача — передать модели смысл и границы функции.

Рекомендуемые поля:

```text
INTENT
RESPONSIBILITY
NON_RESPONSIBILITIES
INPUTS
OUTPUTS
STATE_CHANGES
SIDE_EFFECTS
PRECONDITIONS
POSTCONDITIONS
INVARIANTS
FAILURE_BEHAVIOR
BUSINESS_RULES
LINKS
TEST_PROPERTIES
AUTOMATON_SPECS         (необязательно; ссылки на одну или несколько спецификаций)
AUTOMATON_TRANSITIONS   (необязательно; ID переходов из связанных спецификаций)
AUTOMATON_ACTIONS       (необязательно; ID действий из связанных спецификаций)
```

Поля `AUTOMATON_SPECS`, `AUTOMATON_TRANSITIONS` и `AUTOMATON_ACTIONS` заполняются только для функций, связанных с одной или несколькими автоматными моделями; для остальных функций они не требуются. Ссылки на переходы и действия должны однозначно разрешаться в пределах указанных спецификаций.

Формальные предусловия, постусловия и инварианты сохраняются как полезный слой, но не исчерпывают контракт.

AI-контракт близок к структурированному docstring по паттерну «описание функции → реализация», но дополнительно является узлом общего графа и содержит ссылки на требования, модуль, инварианты, тесты и логи.

GRACE соответствует Spec-Driven Development, но делает спецификацию многоуровневой:

```text
требования → граф → контракт модуля → контракт функции → код
```
