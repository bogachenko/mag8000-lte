# 15. Работа с legacy-кодом

## 15.1. Восстановление контрактов

Для legacy-систем применяется обратный путь:

```text
Существующий код
→ кандидаты поведенческих контрактов
→ граф фактического поведения
→ сравнение с тестами, логами, call sites и требованиями
→ утверждённые контракты
→ безопасное изменение
```

Ключевое правило:

```text
Восстановленный контракт ≠ исходный замысел.
```

Он является гипотезой о текущем поведении. Legacy-код может содержать ошибку, поэтому нельзя автоматически превращать всё текущее поведение в норму.

Для каждого кандидата фиксируется происхождение:

```text
INFERRED_FROM_CODE
COMPILED
SUPPORTED_BY_TESTS
SUPPORTED_BY_CALL_SITES
CONSISTENT_WITH_REQUIREMENTS
HUMAN_APPROVED
```

Только утверждённый контракт становится семантическим щитом.

## 15.2. Изменение legacy-кода

Перед рефакторингом агент должен получить:

```text
граф проекта
+ контракт модуля
+ контракт функции
+ связанные тесты
+ релевантные traces
```

Он должен понимать не только, что код делает сейчас, но и зачем он существует.

---

Если для изменяемого legacy-модуля решение о применимости автоматного программирования ещё не зафиксировано, его определяют по восстановленному и сопоставленному с требованиями `MODULE_CONTRACT`, отдельно для каждого выявленного контура управляющего поведения. Один legacy-модуль может потребовать нескольких `AUTOMATON_SPEC`. Текущий код, тесты, call sites и traces могут служить свидетельствами для восстановления поведения, но сам код не считается доказательством правильного замысла.

Если для контура принято `REQUIRED`, соответствующая `AUTOMATON_SPEC` создаётся и утверждается до изменения его управляющей логики. Если данных недостаточно, фиксируется `UNRESOLVED`; нельзя объявлять автоматную модель подтверждённой только потому, что удалось вывести её из текущего кода. Повторная оценка и обновление спецификаций выполняются только для затронутого контура и его зависимой ветви графа.
