# 12. Автоматическое тестирование для AI

Для автономных и swarm-агентов нужны комплексные автоматические тесты с богатыми логами.

```text
Корректность =
результат тестов
+ соблюдение контрактов
+ сохранение инвариантов
+ допустимый путь выполнения
+ отсутствие регрессий
```

## 12.1. Два уровня обратной связи

Каждый тест должен давать бинарный сигнал для приёмки:

```text
PASS / FAIL
```

И диагностический сигнал для исправления:

- нарушенное свойство;
- ожидаемое состояние;
- фактическое состояние;
- первую точку расхождения;
- trace ID;
- семантический адрес кода;
- связанные требования и контракты.

Пример:

```xml
<TEST_FEEDBACK id="TF-ORDER-004">
    <VERDICT>FAIL</VERDICT>

    <TEST ref="TEST-ORDER-004" />
    <REQUIREMENT ref="UC-ORDER-001" />
    <CONTRACT ref="CONTRACT-VALIDATE-ORDER" />
    <TRACE ref="TRACE-8F21A7" />

    <FAILED_PROPERTY ref="INV-ORDER-001">
        Итоговая сумма заказа должна быть положительной.
    </FAILED_PROPERTY>

    <EXPECTED>total_amount&gt;0</EXPECTED>
    <ACTUAL>total_amount=-500</ACTUAL>

    <FIRST_DIVERGENCE>
        <FUNCTION ref="calculate_order_total" />
        <SEMANTIC_BLOCK ref="DISCOUNT-APPLICATION" />
    </FIRST_DIVERGENCE>
</TEST_FEEDBACK>
```

## 12.2. Строгие проверки нельзя заменять LLM-вердиктом

Обязательная иерархия:

```text
1. Типы и схемы
2. Ограничения базы данных
3. Формальные инварианты
4. Детерминированные assertions
5. Регрессионные и интеграционные тесты
6. Семантически размеченная трасса
7. Независимая LLM-оценка
8. Человеческая проверка критических изменений
```

LLM не должна единолично подтверждать финансовые суммы, проводки, права доступа, балансы, идемпотентность, уникальность, типы, схемы и обязательные состояния.

Для них применяются обычные проверки:

```text
assert
property-based test
schema validation
state-transition check
database constraint
type check
```

## 12.3. TDD

TDD не является антипаттерном само по себе.

Риск возникает в сценарии:

```text
агент видит узкий набор тестов
→ многократно подгоняет реализацию
→ принимает зелёные тесты за полную корректность
```

GRACE расширяет TDD:

```text
Contract-Driven Development
+ Property-Based Testing
+ Differential Testing
+ Agent-Based Testing
+ Log-Driven Development
```

## 12.4. Мысленные и исполняемые тесты

```text
Мысленный тест = проверка плана и гипотеза.
Исполняемый тест = наблюдаемое свидетельство.
```

Мысленная симуляция не заменяет запуск.

## 12.5. Контрактно-обоснованные тесты

Исполняемые тесты должны выводиться из утверждённых контрактов.

В контракт включается не большой модуль тестового кода, а проверяемые свойства:

```xml
<ACCEPTANCE_PROPERTIES>
    <PROPERTY id="PROP-ORDER-001">
        После сохранения заказ существует ровно в одном экземпляре.
    </PROPERTY>
</ACCEPTANCE_PROPERTIES>

<FORBIDDEN_BEHAVIOR>
    <RULE id="FORBID-ORDER-001">
        Повторный вызов не должен создавать дубликат заказа.
    </RULE>
</FORBIDDEN_BEHAVIOR>

<TEST_LINKS>
    <TEST ref="TEST-ORDER-CREATE" />
    <TEST ref="TEST-ORDER-IDEMPOTENCY" />
</TEST_LINKS>
```

Полный тест остаётся отдельным семантически адресуемым узлом графа и загружается только при необходимости.
