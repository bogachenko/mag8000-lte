## Этап 5. Контракты классов и функций

Контракт функции не создаётся изолированно. Он является локальным уточнением:

```text
Требование
→ архитектурный граф
→ контракт модуля
→ контракт функции
```

Контракт функции должен описывать:

- намерение;
- ответственность;
- границы ответственности;
- входы и выходы;
- состояния;
- побочные эффекты;
- предусловия;
- постусловия;
- инварианты;
- поведение при ошибках;
- бизнес-правила;
- ссылки на вышестоящие узлы;
- критерии проверки.

Пример:

```xml
<FUNCTION_CONTRACT id="CONTRACT-VALIDATE-ORDER">
    <FUNCTION>validate_order</FUNCTION>

    <INTENT>
        Определить, может ли черновик заказа перейти к резервированию.
    </INTENT>

    <RESPONSIBILITY>
        Проверить обязательные поля, статус клиента и положительность количества.
    </RESPONSIBILITY>

    <NON_RESPONSIBILITIES>
        <RULE>Не резервировать товар.</RULE>
        <RULE>Не сохранять заказ.</RULE>
        <RULE>Не изменять состояние клиента.</RULE>
    </NON_RESPONSIBILITIES>

    <INPUTS>
        <INPUT name="order_draft" type="OrderDraft" />
    </INPUTS>

    <OUTPUTS>
        <OUTPUT type="OrderValidationResult" />
    </OUTPUTS>

    <SIDE_EFFECTS>
        <FORBIDDEN>Любое изменение постоянного состояния.</FORBIDDEN>
    </SIDE_EFFECTS>

    <FAILURE_BEHAVIOR>
        Возвращать типизированную причину отказа.
    </FAILURE_BEHAVIOR>

    <LINKS>
        <MODULE_CONTRACT ref="CONTRACT-MOD-ORDER" />
        <REQUIREMENT ref="UC-ORDER-001" />
        <INVARIANT ref="INV-ORDER-001" />
    </LINKS>
</FUNCTION_CONTRACT>
```

Если функция реализует переход или действие одной или нескольких автоматных моделей, её обычный `FUNCTION_CONTRACT` должен ссылаться на соответствующие `AUTOMATON_SPEC` и ID переходов и/или действий. Отдельный тип контракта для автоматных функций не вводится. Контракт функции не дублирует таблицы переходов и не должен противоречить ни одной из связанных автоматных спецификаций. Функции вычислений и побочных действий сохраняют обычные контракты GRACE.

## Этап 6. Мысленные тесты

До генерации реализации модель пошагово прогоняет основные сценарии:

```text
вход → проверки → изменения состояния → ветвления → результат
```

Мысленный тест нужен для проверки плана, поиска пропущенных переходов, обнаружения неописанных ошибок, уточнения потоков данных и проектирования будущих тестов.

Но мысленный тест не является доказательством выполнения. Это гипотеза, которую должен подтвердить исполняемый тест.

Для модулей с `REQUIRED` мысленные сценарии дополнительно проверяют последовательности событий, допустимые и недопустимые переходы, граничные состояния, обработку отказов и сохранение инвариантов. Эти сценарии должны быть связаны с ID состояний и переходов `AUTOMATON_SPEC`; мысленная проверка не заменяет формальную или исполняемую проверку.

## Этап 7. Генерация кода

Код генерируется как компиляция утверждённого контракта.

```text
Нет утверждённого контракта — нет реализации.
```

Модель не должна одновременно придумывать назначение функции и её реализацию.

Для модулей с `REQUIRED` управляющая логика реализуется в соответствии с утверждённой `AUTOMATON_SPEC`. Реализация не должна независимо переопределять состояния, условия и переходы. Генерация кода из модели применяется, если это поддерживается выбранным инструментарием; при ручной реализации соответствие модели всё равно должно проверяться отдельно. Действия автомата могут делегироваться обычным функциям с контрактами GRACE.

## Этап 8. Верификация

После генерации проверяются:

- компиляция;
- типы;
- схемы;
- предусловия и постусловия;
- инварианты;
- побочные эффекты;
- бизнес-сценарии;
- состояния;
- траектории выполнения;
- отсутствие регрессий.

При ошибке возврат выполняется на уровень причины:

```text
Ошибка понимания задачи → RequirementsAnalysis
Ошибка архитектуры → DevelopmentPlan
Ошибка ответственности → контракт
Ошибка реализации → код
Ошибка критерия → отдельное согласованное изменение теста или контракта
```

Нельзя автоматически переписывать контракт под уже созданный ошибочный код.

---

Для модулей с `REQUIRED` верификация включает отдельные проверки:

- корректности автоматной модели и выполнения заданных для неё формальных свойств;
- соответствия реализации утверждённой автоматной модели.

Эти проверки не взаимозаменяемы. Model Checking подтверждает свойства проверенной модели, но сам по себе не доказывает, что исходный код ей соответствует. Соответствие реализации проверяется отдельно выбранными средствами (например, генерацией кода с контролируемой семантикой, тестами переходов, трассами и проверками соответствия).
