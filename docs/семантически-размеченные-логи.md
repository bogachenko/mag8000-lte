# 10. Семантически размеченные логи

Большой лог нельзя оставлять хаотичным потоком строк. Каждое значимое событие должно иметь семантические координаты.

Минимальные поля:

```text
EVENT_ID
TIMESTAMP
SEVERITY
TRACE_ID / CORRELATION_ID
MODULE
FUNCTION / SEMANTIC_BLOCK
CONTRACT_ID
REQUIREMENT_ID
INTENT
RESULT
REASON
STRUCTURED_DATA
```

Пример:

```xml
<LOG_EVENT
    id="EVT-ORDER-VALIDATION-FAILED"
    timestamp="2026-07-21T18:42:13.821Z"
    severity="ERROR"
    trace_id="TRACE-8F21A7"
    module="MOD-ORDER"
    function="validate_order"
    contract="CONTRACT-VALIDATE-ORDER"
    requirement="UC-ORDER-001">

    <INTENT>Проверить возможность перехода заказа к резервированию</INTENT>
    <RESULT>VALIDATION_FAILED</RESULT>
    <REASON>INVALID_QUANTITY</REASON>

    <DATA>
        order_id=483921
        product_id=91244
        quantity=-2
    </DATA>
</LOG_EVENT>
```

Для большого файла создаётся LOG_MAP:

```xml
<LOG_MAP id="LOG-ORDERFLOW-2026-07-21">
    <TRACE
        id="TRACE-8F21A7"
        start_event="EVT-ORDER-CREATE-START"
        final_event="EVT-ORDER-VALIDATION-FAILED"
        status="FAILED"
        module="MOD-ORDER" />

    <CRITICAL_EVENTS>
        <EVENT ref="EVT-ORDER-VALIDATION-FAILED" />
    </CRITICAL_EVENTS>
</LOG_MAP>
```

Порядок анализа:

```text
LOG_MAP
→ ключевая trace
→ релевантные события
→ контракт
→ блок кода
→ причина
```

Агент не должен рассчитывать на последовательное чтение всего файла.
