# 4. Основные артефакты

## 4.1. RequirementsAnalysis.xml

Важно различать:

```text
RequirementsAnalysis — процесс анализа.
RequirementsAnalysis.xml — артефакт.
Семантический граф требований — его основное содержимое.
```

В нём фиксируются:

- цель системы;
- акторы;
- сценарии Actor–Action–Goal;
- бизнес-процессы;
- сущности;
- состояния;
- бизнес-правила;
- ограничения;
- инварианты;
- ошибочные сценарии;
- граничные случаи;
- критерии правильного результата;
- связи между элементами.

Пример:

```xml
<REQUIREMENTS_ANALYSIS id="RA-ORDERFLOW">
    <PROJECT_GOAL id="GOAL-001">
        Позволить продавцу создавать и контролировать заказы
        без нарушения складских и финансовых инвариантов.
    </PROJECT_GOAL>

    <ACTOR id="ACTOR-SELLER">Продавец</ACTOR>

    <USE_CASE id="UC-ORDER-001">
        <ACTOR ref="ACTOR-SELLER" />
        <ACTION>Создаёт заказ покупателя</ACTION>
        <GOAL>Зафиксировать состав и стоимость заказа</GOAL>
        <STARTS_PROCESS ref="BP-ORDER-CREATION" />
    </USE_CASE>

    <BUSINESS_PROCESS id="BP-ORDER-CREATION">
        <STEP order="1" ref="STEP-VALIDATE-CUSTOMER" />
        <STEP order="2" ref="STEP-CALCULATE-TOTAL" />
        <STEP order="3" ref="STEP-RESERVE-STOCK" />
        <STEP order="4" ref="STEP-SAVE-ORDER" />
    </BUSINESS_PROCESS>

    <INVARIANT id="INV-ORDER-001">
        Проведённый заказ не может иметь отрицательную итоговую сумму.
    </INVARIANT>
</REQUIREMENTS_ANALYSIS>
```

## 4.2. Technology.xml

Фиксирует язык, фреймворки, библиотеки, точные версии, совместимость, форматы данных, среду исполнения, инфраструктуру, безопасность и причины выбора.

Технологии выбираются после требований и должны обслуживать утверждённую задачу. Если для компонентов потребуется `AUTOMATON_SPEC`, выбор технологий должен учитывать совместимость нотации автоматной модели со средствами её проверки и, при необходимости, генерации кода. Конкретные инструменты фиксируются в `Technology.xml`, когда они действительно нужны проекту.

## 4.3. DevelopmentPlan.xml

Содержит архитектурный граф:

- модули;
- классы или сервисы;
- границы ответственности;
- потоки данных;
- зависимости;
- состояния;
- внешние интеграции;
- связь архитектуры с бизнес-процессами;
- последовательность реализации;
- риски;
- мысленные проверки;
- предварительно выделенные модули-кандидаты и известные контуры управляющего поведения для оценки автоматного программирования (без фиксации окончательного решения).

Пример:

```xml
<DEVELOPMENT_PLAN id="DP-ORDERFLOW">
    <MODULE id="MOD-ORDER">
        <RESPONSIBILITY>Управлять жизненным циклом заказа.</RESPONSIBILITY>
        <IMPLEMENTS ref="BP-ORDER-CREATION" />
        <PRESERVES ref="INV-ORDER-001" />
    </MODULE>

    <MODULE id="MOD-STOCK">
        <RESPONSIBILITY>Управлять резервированием остатков.</RESPONSIBILITY>
    </MODULE>

    <MENTAL_TEST id="MT-ORDER-001">
        <INPUT>Заказ из двух доступных товаров</INPUT>
        <EXPECTED_PATH>
            VALIDATE_CUSTOMER → CALCULATE_TOTAL → RESERVE_STOCK → SAVE_ORDER
        </EXPECTED_PATH>
    </MENTAL_TEST>
</DEVELOPMENT_PLAN>
```

## 4.4. AUTOMATON_SPEC

Самостоятельный, версионируемый артефакт, формализующий один определённый контур управляющего поведения модуля, для которого соответствующая оценка в `MODULE_CONTRACT` имеет решение `REQUIRED`.

Один `MODULE_CONTRACT` может быть связан с несколькими `AUTOMATON_SPEC`, если модуль управляет несколькими самостоятельными контурами поведения (например, жизненным циклом заказа и жизненным циклом приглашения). По умолчанию один `AUTOMATON_SPEC` описывает один такой контур. Независимые автоматы не объединяются только ради принадлежности одному модулю. Если автоматы взаимодействуют, их взаимодействие, общие события, обмен данными и порядок координации должны быть явно описаны.

Каждый `AUTOMATON_SPEC` создаётся после утверждения соответствующей оценки и контракта модуля, до создания контрактов классов и функций. Он не заменяет требования, бизнес-процессы или контракт модуля, а уточняет допустимое поведение соответствующего контура на уровне автомата.

Спецификация содержит:

- начальное состояние и множество управляющих состояний;
- входные события и команды;
- условия (guards) переходов;
- переходы между состояниями;
- действия и выходные воздействия, связанные с переходами;
- поведение для недопустимых или неописанных событий;
- инварианты и формальные свойства, подлежащие проверке;
- стабильные ID состояний, событий и переходов;
- ссылку на соответствующую запись `AUTOMATON_ASSESSMENT`, а также ссылки на требования, бизнес-процессы и `MODULE_CONTRACT`.

### Однозначность и детерминированность

Для каждого состояния и входного события спецификация должна однозначно определять обработку:

- условия (guards) всех переходов-кандидатов вычисляются по явно определённым данным и контексту одного шага обработки;
- для одной комбинации текущего состояния, события и контекста может быть выбран не более чем один переход;
- если несколько guards могут оказаться истинными одновременно, спецификация должна либо доказуемо исключать такое пересечение, либо задавать явный приоритет; приоритеты конкурирующих переходов должны образовывать однозначный порядок без равных значений, а правило выбора (например, наибольший приоритет) должно быть явно указано;
- если ни один переход не подходит, должно быть явно определено поведение для соответствующей комбинации состояния и события (например, `REJECT`, `IGNORE` или `DEFER`); для `DEFER` дополнительно задаются правила хранения события и его повторной обработки;
- порядок обработки событий должен быть определён. По умолчанию один автомат обрабатывает события последовательно; при конкурентном поступлении событий среда или спецификация должны задавать воспроизводимый порядок их принятия и обработки. Если используется очередь, порядок принятия должен фиксироваться, например, монотонным sequence number; одних временных меток недостаточно, если они могут совпадать;
- порядок выполнения действий перехода, момент фиксации нового состояния и поведение при ошибке действия должны быть определены;
- события, порождённые действиями автомата, по умолчанию ставятся в очередь и обрабатываются после завершения текущего перехода; иной порядок допускается только при явном описании его семантики.

Приоритеты переходов, если они используются, должны быть явными и однозначными. Неопределённый порядок, неявный выбор первого совпавшего перехода и зависимость результата от гонки событий не допускаются.

Формат модели, нотация, средства проверки и возможная генерация кода определяются выбранными технологиями. Спецификация должна быть однозначной, проверяемой и связанной с остальными артефактами GRACE.
