# 22. Антипаттерны GRACE

## Сразу писать код

```text
Неформальный запрос → большой модуль кода
```

Модель вынуждена одновременно придумывать архитектуру, контракты и реализацию.

## Строить архитектуру после реализации

Архитектура должна предшествовать функциям.

## Создавать контракт функции изолированно

Контракт функции должен следовать из контракта модуля и графа.

## Выводить замысел только из текущего кода

Особенно опасно для legacy-систем.

## Автоматически обновлять контракт под патч

Сначала меняется замысел, затем реализация.

## Передавать агенту весь тестовый репозиторий без навигации

Тесты должны быть семантически адресуемыми и загружаться по необходимости.

## Заменять строгие проверки LLM-судьёй

Вероятностная оценка не заменяет типы, балансы, права и инварианты.

## Удалять assertions

Удаляются только бессодержательные или хрупкие проверки. Существенные инварианты остаются детерминированными.

## Считать мысленную симуляцию исполнением

Она не учитывает фактическую среду и реальные побочные эффекты.

## Считать зелёные узкие тесты доказательством готовности

Нужны регрессия, свойства, скрытые сценарии и traces.

## Хранить большие логи без якорей

Без trace_id, event_id, контрактов и карты агент теряет навигацию.

## Использовать GUI как единственный интерфейс тестирования

Нужны CLI, API и Tools.

## Использовать JSON как основной контейнер большого LLM-контекста

Для больших документов предпочтительны XML-like, Markdown и явные поля.

## Позволять одному агенту менять код, тест и критерий

Это разрушает независимость проверки.
