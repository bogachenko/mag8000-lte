# 25. Нормативные правила

## Обязательно

- начинать с RequirementsAnalysis;
- строить явный семантический граф;
- связывать все артефакты стабильными ID;
- утверждать верхний уровень до детализации;
- создавать контракты до реализации;
- проверять патчи по контрактам;
- использовать семантические якоря;
- иметь автоматизированные тесты;
- проверять не только результат, но и траекторию;
- сохранять детерминированные assertions;
- размечать значимые события логов;
- предоставлять агенту CLI/API/Tools;
- отделять реализацию от независимой проверки;
- синхронизировать граф, контракты, код, тесты и логи;

### Автоматное программирование

- На этапе архитектурного планирования выделять модули-кандидаты и самостоятельные контуры управляющего поведения внутри них; окончательную оценку выполнять в `MODULE_CONTRACT` отдельно для каждого контура либо для модуля в целом, если контуры не выделены.
- Фиксировать каждую оценку отдельной записью `AUTOMATON_ASSESSMENT` с уникальным ID, `SCOPE`, результатами критериев (`YES`, `NO`, `UNKNOWN`), обоснованием и ссылками на свидетельства. Решение (`REQUIRED`, `NOT_REQUIRED`, `UNRESOLVED`) должно соответствовать формальному правилу раздела 5.
- Один модуль может иметь несколько `AUTOMATON_ASSESSMENT` и несколько связанных `AUTOMATON_SPEC`; каждый автомат должен описывать определённый контур, а взаимодействие автоматов должно быть явно специфицировано.
- При `REQUIRED` создавать и утверждать соответствующую `AUTOMATON_SPEC` после контракта модуля и до контрактов функций.
- При `NOT_REQUIRED` использовать обычный процесс реализации GRACE без автоматной спецификации.
- При `UNRESOLVED` не передавать в реализацию соответствующий контур; если его нельзя изолировать от остальной ответственности, блокировать модуль до устранения неопределённости.
- Контракты функций, реализующих переходы или действия одного или нескольких автоматов, должны ссылаться на соответствующие `AUTOMATON_SPEC` и ID переходов/действий; отдельный тип контракта для таких функций не вводится.
- Каждая автоматная спецификация должна однозначно определять выбор перехода, поведение при отсутствии подходящего перехода, порядок обработки событий, порядок действий и поведение при ошибках. Неявный выбор перехода и зависимость от незафиксированной гонки событий запрещены.
- Реализация управляющей логики должна соответствовать утверждённым автоматным спецификациям. Проверку модели и проверку соответствия реализации выполнять раздельно.
- При изменении требований, архитектуры или поведения повторно оценивать применимость только тогда, когда изменение затрагивает исходные критерии или их обоснование. Существующее решение сохранять между вызовами агентов и не пересматривать без зафиксированных оснований.

Это правило определяет обязательность оценки и применения автоматного программирования, но не требует представлять автоматами вычислительные функции и компоненты, не удовлетворяющие критериям.

## Нельзя

- генерировать большой модуль напрямую из неформального запроса;
- считать текущий legacy-код исходным замыслом;
- заменять строгие свойства субъективным LLM-вердиктом;
- позволять агенту незаметно ослаблять критерии;
- считать мысленные тесты доказательством;
- считать зелёные smoke-тесты полной проверкой;
- оставлять большие документы и логи без карты и якорей;
- создавать контракты функций без связи с архитектурой.

## Допустимо как дополнительный слой

- LLM-анализ трасс;
- семантическая оценка неоднозначных бизнес-сценариев;
- восстановление кандидатов контрактов;
- агентные Markdown-процедуры;
- независимый LLM-рецензент;
- автоматическая регенерация затронутых блоков.

Эти механизмы должны опираться на наблюдаемые артефакты и не отменять детерминированные гарантии.
